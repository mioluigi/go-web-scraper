# Project Constitution — Crawling and Scraping the Web (Go + Colly)

> **Purpose.** The non-negotiable rules for this project. Every spec, plan, task and line of code is checked
> against them. A conflicting decision either changes or amends this file deliberately, with a note in
> `docs/decisions.md`.
>
> **Source of authority.** The Week 7 assignment and rubric (`docs/assignment-and-rubric.md`), carried forward
> from Week 6 (SFEDD v2.0, Articles 1–8) with changes for a program that talks to **someone else's website**.
> Tags: **[C]** Coding · **[T]** Testing & metrics · **[D]** Design · **[Doc]** Documentation ·
> **[A]** Application. *New or changed this week* is marked **(W7)**.

## Article 1 — Correctness before speed

1.1 **(W7)** A concurrent crawl is trusted only when it yields **the same records as a sequential crawl**
(parallelism 1) of the same pages, compared by a program, ignoring order and timestamps. **[T]**
1.2 Speed is reported only for a configuration that has passed 1.1. **[T]**
1.3 Every number in the README — tables **and** headline figures — is generated by script from saved results;
prose that cites them is re-checked whenever results change. **[Doc]**
1.4 Concurrent code passes the race detector (`go test -race`). **[T]**
1.5 **(W7)** Extraction quality is tested on **saved real pages** with known content (title present, no CSS,
no `[edit]`, no citation markers such as `[1]`, words not glued together). **[T]**

## Article 2 — Idiomatic, readable Go (McConnell 2004, ch. 32) **[C]**

2.1 Go modules; `gofmt` and `go vet` clean.
2.2 Meaningful, specific names; not abstract, not overly long.
2.3 No useless temporary variables or intermediate results.
2.4 Functions do one thing; large blocks become small, named functions.
2.5 Plain `if/else` and `for`; distribute the NOT in complex Boolean expressions.
2.6 Every exported identifier has a doc comment; comments explain *why*.
2.7 Errors are returned and handled; **no `panic`** for a bad page. One failed URL is reported in its record
and does not stop the others.
2.8 Every goroutine has an owner and an end; output has **a single writer**; no goroutine outlives a crawl.

## Article 3 — Test-first, measured **[T]**

3.1 Failing test before implementation of every critical component; **mutation check** important tests (a
mutation that only breaks compilation does not count).
3.2 Standard `testing`; table-driven; **tests never touch the live internet** — they use a local
`httptest` server serving saved pages. **(W7)**
3.3 Benchmarks with `testing.B` and allocation reporting; CPU and memory profiles kept.
3.4 Compared configurations do **the same work on the same machine**; medians of repeated runs; printing
outside timed code. **(W7)** A comparison with another tool (Scrapy) equalises concurrency, delays and caching,
and says so.
3.5 Guards, scripts and acceptance checks are themselves tested on a passing and a failing case; exit codes
are tested on the **built binary**.

## Article 4 — Clean, reusable design **[D]**

4.1 **(W7)** Crawling and extraction live in **reusable packages** with no printing and no `os.Exit`; the
site-specific part (which HTML to keep) is a small, replaceable component, so the same crawler serves
another site by swapping it. The command-line program is a thin layer.
4.2 Sequential and concurrent runs use **the same code path**; only the parallelism setting differs.
4.3 Pin every dependency version (`go.mod`, `go.sum`); `go.sum` is generated on Luis's Mac. **(W7)**

## Article 5 — Documentation and Git hygiene **[Doc]**

5.1 One `README.md` is the complete documentation: purpose, roles of programs and data, build, run, test,
benchmark, results, recommendation.
5.2 One task per commit, message starts with the task ID; specs, plan, tasks, reviews, decisions in the repo.
5.3 README **GenAI Tools** section; AI dialogs in `docs/ai-dialogs/` with a `README.md` index.
5.4 `scripts/acceptance.sh` is committed and passes on a **fresh clone** before submission.

## Article 6 — A finished, friendly application **[A]**

6.1 Documented builds produce a macOS binary, a Windows `.exe` and a macOS `.app`.
6.2 The program **runs to completion with no arguments**, crawling the ten assignment URLs.
6.3 User input (URL list, flags) is validated; bad input yields a clear message and a non-zero exit code.
6.4 A finished run tells the user, in plain words, how many pages succeeded, which failed and why, and where
the output file is. Logs go to standard error.

## Article 7 — How we work with AI tools

7.1 Claude Code is the only tool that writes files in this repository during a task.
7.2 Gemini (web) reviews the spec and the finished repository; it receives the **files** and must cite file and
section for every claim.
7.3 Luis approves spec, plan and tasks, and reads every diff before it is committed.
7.4 If implementation shows the spec is wrong, update the spec first.
7.5 Every review finding gets a recorded decision with a reason; testable claims are tested first.
7.6 Spike before planning; inherited code is run unchanged; predictions are checked and corrected in writing.
7.7 Claude verifies every hand-off and push landed before building on it.

## Article 8 — Data and privacy

8.1 Inputs and fixtures pass the data gate (`scripts/check-inputs.sh`) before their first commit.
8.2 **(W7)** No personal email address appears in committed **files** or in the program's traffic: the
User-Agent's contact field is the public repository URL, not an inbox. (Commit metadata follows Luis's usual
Git identity.)
8.3 **(W7)** Saved Wikipedia pages and the `.jl` output are **CC BY-SA** content: the README credits
Wikipedia and states the licence; fixtures record their source URL and capture date.
8.4 Luis decides any history rewrite; it touches only our own commits.

## Article 9 — Respect for the target site **(W7, new)**

9.1 The crawler identifies itself with a descriptive User-Agent in the Wikimedia format
`<client>/<version> (<contact>) <library>/<version>`; never a browser imitation, never the library default.
9.2 It **obeys `robots.txt`** and stays on the allowed domains.
9.3 It **bounds parallelism per domain** and supports a delay; defaults are modest, and the README states
them.
9.4 During development, live requests are kept to the minimum: tests use saved pages, and repeated runs use
an opt-in cache.
